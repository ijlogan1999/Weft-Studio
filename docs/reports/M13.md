# Milestone 13 report: hardening, performance and the installer

M13 is the last planned milestone. It stress-tests the audio engine against the document,
measures the performance targets, replaces the stopgap resampler, and builds a Windows installer
in CI. The [HW] acceptance tests need a real Windows PC, interface and MIDI keyboard; they now
have a checklist, [docs/hardware-test-pass.md](../hardware-test-pass.md), ready for that pass.

## What works

- **Fuzzing the engine against the document (AT-RT-2).** A test makes 10,000 random edits while the
  project plays. It covers 24 kinds of edit: moving, trimming, splitting and fading regions, notes,
  controllers, mixer, insert and send changes, plug-in parameters, automation, tempo and signature,
  adding and deleting tracks, and undo and redo. One edit in five is made by a second user and
  merged through the sync protocol. Every block must render inside its deadline, with no
  allocation or locking on the audio thread, and both users must end with the same document. The
  random seed changes each run, and Catch2 prints it so a failure can be replayed.
- **Better playback when the device can't run at the project's rate.** When a file's rate differs
  from the device's (for example a 48 kHz project on a 44.1 kHz interface), playback now uses a
  windowed-sinc resampler instead of cubic interpolation. A 10 kHz tone used to be off by 2%; now
  the error is 88 dB below the signal. Sounds above the device's Nyquist frequency are filtered
  out (by 88 dB) instead of folding back down as audible noise.
- **The performance targets are measured.**
  - Relay capacity: 50 rooms of 8 clients, each editing once a second, on a relay with two worker
    threads. Every change reached the other 7 clients, with p50 46 ms and p95 58 ms against a
    150 ms limit. CI now runs this on every push.
  - Loading a document with 200 tracks, 5,000 regions and 200,000 notes takes 2.2 to 2.3 s
    against the 3 s limit, measured in a Release build (CI enforces the limit).
  - Edit-to-remote is inside its target: about 60 ms p95 on localhost, against 150 ms plus the
    round trip.
- **A Windows installer.** A new CI job builds a Release, packages it as a setup .exe and a ZIP, then
  installs it silently, checks the files are there and uninstalls it. The installer adds Start Menu
  and desktop shortcuts and an uninstaller, removes an older version before upgrading, and brings
  its own Visual C++ runtime, so a fresh Windows PC needs nothing else. Download it from the
  `WeftStudio-windows-installer` artifact of a CI run.
- **The CPU meter's tooltip shows the dropout and disk underrun counts**, which the hardware pass
  reads off.

## Decisions made

- D-AT-3 (spec 06): the AT-REC-6 reference machine is a 2019-or-later 4-core/8-thread PC with 16 GB
  RAM and an SSD, running Windows 11, with an 8-input USB interface and its own ASIO driver.
- D-AT-4 (spec 06): the AT-PLG-1 plug-ins are TDR Nova, Valhalla Supermassive, MCompressor,
  Airwindows Consolidated and SPAN (effects), and Surge XT and Dexed (instruments).
- D-ARCH-49: the test device measures deadline misses in CPU time, not wall time.
- D-ARCH-50: resampled playback uses a Kaiser-windowed sinc.
- D-ARCH-51: the installer is built with CPack and NSIS.
- D-ARCH-52: how relay capacity is measured.

## Fixed along the way

- **The test device mistook a busy machine for a slow engine.** The fuzz test's first runs failed
  one block in 10,000. The block needed 0.4 ms of work, but the test machine paused the thread
  for longer than the 5 ms deadline. The test device now counts only the time the engine actually
  spends working. The app's own CPU meter and dropout counter still measure real time, as they
  should.

- **The fuzz test's own bug.** Its first Windows run crashed. The test held a region past the edit
  that replaced it. AddressSanitizer found it on every seed. The test now keeps what it picks alive,
  and it draws its random numbers the same way on every compiler, so a seed printed on Windows
  replays the same edits on Linux. The whole engine suite also runs clean under AddressSanitizer.

## Stubbed or not yet done

- **The hardware pass hasn't been run.** It needs a Windows PC that meets the reference spec, an
  8-input interface and a MIDI keyboard. The checklist is ready.
- The installer isn't code-signed, so Windows SmartScreen will warn on first run. Signing needs a
  certificate.
- The app has no icon of its own yet. It shows the default one in the Start Menu and taskbar until
  there's artwork.
- The installer has WASAPI only. ASIO is in it once release builds get the ASIO SDK.

## Known issues

- **Needs your call (unchanged):** where the public relay will be hosted, the donation link, and
  how release builds get the ASIO SDK (D-ARCH-14). The last one now also decides whether the
  installer offers ASIO.
- Relay fan-out takes 8 ms (median) with one room and 46 ms with 50. The 400 test clients run on
  the same 4-core machine as the relay, each on its own thread, so part of that rise is the clients
  competing for CPU rather than the relay. I haven't separated the two; the target is met either way.
- The fuzz test takes about a minute in a Debug build.
