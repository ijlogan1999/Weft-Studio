# Milestone 1 report: document core

## What works

- **CRDT document layer.** `weft::doc::Document` reads and writes any path in the Automerge document (map keys, list indexes, and list elements by id) through a small binary codec shared with the Rust crate. Writes stay pending until `commit`, so one user action is one CRDT change.
- **Typed project model (spec 03).** Every entity in the data model has a C++ type that reads leniently: missing or malformed fields fall back to defaults and out-of-range values are clamped.
- **Projection with read-time repair (spec 03 §10.4).** `Projector` builds the model from the document and refreshes only the entities a change touched. All seven repairs are implemented and tested with two replicas making concurrent edits:
  1. duplicate list entries keep the first;
  2. tracks missing from the track order are appended, sorted by id;
  3. orphaned regions go to a Recovered track with a deterministic id;
  4. two tempo or signature points at one position: the greater id wins and is flagged;
  5. routing cycles: the newest edge is disabled;
  6. duplicate automation lanes are unioned;
  7. out-of-range values are clamped.
- **Commands.** Projects, tracks, regions, notes, plug-ins, sends, automation, tempo, signatures and markers. The region commands are create, move, trim, split, join, delete, fade, gain, mute and quantize. Each command validates first, so a rejected command writes nothing and sets a status message. Limits are enforced: 15 inserts, 8 sends, no feedback loops, and the initial tempo and signature can't be deleted.
- **Per-user undo/redo (05 §6).** Undo only restores fields that still hold this user's value, skips objects someone else deleted (with a status message), and re-creates deleted objects with their original ids. Gestures (`beginGesture` / updates / `endGesture`) make a whole drag one change and one undo step.
- **Tempo and signature maps** (step tempo, tick↔sample, bar starts across meter changes) and the **quantize math** from W-5 (strength, swing).
- **Local persistence.**
  - The project folder is `<Name>.weft/` with `project.automerge`, `Media/`, `Bounces/`, `Cache/` and `Recovery/`.
  - Saving is atomic: a temp file is written, fsynced, then renamed over the old one.
  - Every committed change is appended to `Recovery/changes.log`, with a CRC per record.
  - On open, Weft offers recovery when the log holds unsaved changes. Recover applies them; Discard archives the log.
  - Projects with a newer schema version are refused without touching the file.
- **`weft-cli` project commands:** `new`, `open [--recover|--discard] [--dump]`, and `demo-edits [--hold]`. The kill test uses `demo-edits --hold`.

Totals in the container: 50 CTest tests, with 37 Catch2 unit cases and 1,380 assertions. The Rust side has 11 tests (10 in `weft-crdt`, 1 in the relay). Linux and Windows CI results are on the PR.

**Load benchmark.** The benchmark project has 200 tracks, 5,000 regions and 200,000 notes (a 4.7 MB file). In a Release build in the dev container, loading the document takes about 1.4 s and building the projection about 1.4 s, so the total is about 2.8 s against a 3 s limit. The Linux CI job runs the benchmark in Release and fails if it goes over 3 s. Two things got it under the limit: skipping change-hash verification on load (D-ARCH-8) and an optimized Rust build of Automerge. The margin is small; see known issues.

## Decisions recorded

- D-ARCH-6 to D-ARCH-11 in `docs/ARCHITECTURE.md` §9: gestures, how undo recognises "still mine", load verification, the recovery-log flush policy, split note rebasing, and the synthetic Recovered track.
- D-DM-19 in spec 03: adding a tempo or signature change where one already exists edits that point.
- D-ARR-4 in spec 02: what counts as contiguous audio for a join, and which fades the joined region keeps.

## Stubbed or not started

- **Joining non-contiguous audio** is rejected with a message. Spec D-ARR-3 says to render a new file, which needs the offline renderer (M7).
- **Remote changes during a gesture** aren't queued yet (D-ARCH-6). Nothing applies remote changes until M10.
- **No UI** is connected to the session yet. The app still shows the M0 placeholder; the arrange window comes in M3.
- **Take folders and comments** are read and written as data. Their commands arrive with recording (M4) and collaboration (M11).
- **Media import** (hashing, WAV normalisation) is M4/M5. `addMedia` only registers a reference.

## Known issues

- **Load time has a small margin:** about 2.8 s against 3 s on the dev container. Slower CI machines or laptops may go over.
  - Automerge's own load accounts for about half of it.
  - Exporting about 1.4 million note fields from Automerge accounts for most of the rest. I tried two faster Automerge read paths, and both were slower.
  - If the limit is missed on real hardware, the fallback in ARCHITECTURE.md §3 applies: store each sequence's notes as a compact binary batch, with coarser merge granularity.
- **The benchmark only runs in Release builds.** Building the 200,000-note project takes about 40 s in Release and over a minute in Debug, so CTest registers it only in Release.
- **Undo across many collaborators:** op-id aliases for re-created objects are kept for the whole session. That is fine for one session's undo history, but the alias table grows with every undo or redo of a delete.
